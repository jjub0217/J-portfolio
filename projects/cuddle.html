01 성능

첫 HTML에서 빠진 이미지를 찾아 홈 화면 로딩 줄이기

홈 화면 | Next.js 서버 컴포넌트, Lighthouse, DebugBear

  • 측정
  • 서버 컴포넌트
  • 시도와 되돌리기

AI 도구로 수정안을 만들고, 채택과 되돌리기는 직접 측정해 정함

문제

홈 화면 LCP(가장 큰 요소가 보이기까지의 시간)가 1.3초였습니다. 그중 0.9초는 브라우저가 이미지 주소를 찾기까지 기다린 시간이었습니다.

원인

홈은 useSearchParams() 때문에 Suspense로 감싸져 있었고, 서버는 이미지 주소가 없는 로딩 중 화면만 먼저 보냈습니다. 그래서 첫 HTML에 이미지가 하나도 없었고, 화면 코드가 실행된 뒤에야 이미지를 찾기 시작했습니다.

해결

로딩 중 화면을 실제 상품 데이터를 가진 서버 컴포넌트로 바꿔 첫 HTML에 이미지가 담기게 했습니다. 60초마다 페이지를 다시 만드는 방식은 그대로 두었습니다.

확인한 방법

시도할 때마다 Lighthouse와 DebugBear로 다시 측정해 채택할지 되돌릴지 정했습니다. 바꾸기 전과 후의 첫 HTML에서 이미지 태그 수도 셌습니다(0개에서 22개).

결과

LCP 1.3초 → 1.0초 (약 23% 단축), 성능 점수 94점 유지

함께 늘어난 값도 있습니다. FCP(첫 콘텐츠가 보이는 시간)는 0.4초에서 0.9초로, CLS(화면 흔들림)는 0에서 0.008로 늘었습니다. 첫 HTML이 커져 첫 화면을 그리기까지 시간이 늘었고, 서버 화면이 실제 화면으로 바뀔 때 작은 흔들림이 생겼습니다.

02 관리 화면

관리 화면 8개를 설정 파일 하나로 만드는 공통 테이블

관리자 화면 | React, TypeScript, React Query

  • 설정 파일
  • 공통 훅
  • 재사용

AI 도구와 함께 구현

문제

회원, 탈퇴, 상품, 커뮤니티 글, 신고 4종까지 관리 화면이 8개였고, 화면마다 표와 필터, 정렬, 페이지 처리가 필요했습니다.

원인

같은 표 기능을 화면마다 따로 만들면 같은 코드를 8번 반복하게 됩니다.

해결

화면을 설정 파일로 정의하는 공통 테이블과 커스텀 훅(useAdminTable)을 만들어 8개 화면을 하나의 구조로 묶었습니다. 열은 글자, 숫자, 금액, 배지, 날짜, 이미지 6종으로 나눴고, 새 화면은 설정 파일 하나와 짧은 페이지 코드로 만듭니다.

확인한 방법

8개 화면을 데모 데이터로 띄워 표, 검색, 정렬, 페이지 이동이 같은 방식으로 동작하는지 직접 확인했습니다.

결과

관리 화면 8개가 공통 테이블과 훅 646줄을 함께 쓰고, 새 화면의 페이지 코드는 7줄입니다.

화면별 설정 파일은 52~124줄입니다.

03 검증

AI 코드 리뷰가 실제 버그만 짚도록 지시문 좁히기

PR 자동 리뷰 | GitHub Actions, Kimi K2

  • 지시문
  • 잘못된 지적 확인
  • 주석

AI 도구와 함께 지시문을 고침, 지적은 직접 동작을 확인해 판단

문제

PR마다 도는 AI 코드 리뷰가 일어나기 어려운 예외 상황과 과한 방어 코드까지 지적해, 리뷰가 길기만 하고 읽히지 않았습니다.

원인

처음 지시문이 코드 품질, 버그, 성능, 보안, 모범 사례를 모두 보게 해서, 실제로 고칠 지적과 그렇지 않은 지적이 섞였습니다.

해결

실제 버그, 명백한 성능 문제, Next.js와 React에서 피해야 할 작성 방식만 보게 지시문을 좁히고, 문제가 없으면 짧게 끝내게 했습니다.

확인한 방법

리뷰가 드롭다운에 Escape 키 처리가 빠졌다고 짚었을 때 직접 동작을 확인했습니다. 방향키는 여는 단추가, Escape는 문서 전체의 키 입력 감지가 따로 잡고 있어 리뷰가 잘못 본 것이었습니다.

결과

리뷰가 헷갈린 곳은 사람도 헷갈린다고 보고, 코드는 그대로 둔 채 의도를 밝히는 주석 3줄을 더했습니다.

처음 지시문

"코드 품질, 잠재적 버그, 성능 이슈, 보안 취약점, 그리고 Next.js/React 모범 사례를 확인해주세요."

모든 것을 보게 해서 지적이 길기만 함

바꾼 지시문

"중점 확인 사항: 실제 버그나 런타임 에러 가능성, 명백한 성능 문제, Next.js/React 안티패턴"
"이론적으로만 가능한 엣지 케이스는 무시 / 과도한 에러 핸들링이나 방어 코딩을 제안하지 마세요 / 문제가 없으면 특이사항 없음으로 짧게 마무리하세요"

04 검증

모든 PR에서 타입 검사, 린트, 테스트, 빌드가 돌게 하기

CI | GitHub Actions, Vitest, Jest

  • PR 검사
  • 나란히 돌리기
  • 테스트 검증

AI 도구와 함께 구현

문제

워크플로가 셋 있었지만 그 안에 타입 검사, 린트, 테스트, 빌드가 없어서, 테스트를 깨뜨린 PR도 병합될 수 있었습니다.

원인

검사는 사람이 손으로 돌리는 것뿐이어서, 잊으면 그대로 통과했습니다.

해결

PR마다 공통 패키지, 앱, 웹 세 작업이 나란히 타입 검사, 린트, 테스트, 빌드를 돌게 했습니다. 한 작업에서 순서대로 돌리면 앞이 깨질 때 뒤를 못 보고 시간도 셋의 합이 되기 때문입니다. 문서만 바뀐 PR은 검사를 건너뛰게 했습니다.

확인한 방법

고친 줄을 일부러 빼 보고 테스트가 실패하는지 확인해, 그 테스트가 정말 그 코드를 지키는지 검증했습니다.

결과

테스트 파일 130개 이상(웹, 앱, 공통 패키지)이 모든 PR에서 돕니다.

나란히 도는 작업 3개

  • shared (vitest) 공통 패키지
  • 앱 (tsc · lint · jest)
  • 웹 (tsc · lint · vitest · build)

05 실시간과 결제

다시 연결된 뒤 앱 화면에 메시지가 안 보이던 문제 고치기

채팅 | WebSocket (STOMP), React Native, Next.js

  • 재연결
  • 구독
  • 직접 시험

AI 도구와 함께 고침, 문제는 직접 시험하다 발견

문제

휴대폰 앱과 웹을 오가며 직접 시험하다가, 연결이 끊겼다 다시 이어진 뒤 앱에서 보낸 메시지가 웹에는 가지만 앱 화면에는 보이지 않는 문제를 발견했습니다.

원인

다시 연결되면 예전 구독은 끊긴 연결에 남은 빈 껍데기인데, 코드는 구독이 이미 있다고 보고 건너뛰었습니다. 그래서 새 연결에는 구독이 없었고, 보내기는 잘 되는데 받기만 오류 없이 멈췄습니다. 웹에서는 다시 연결될 때마다 화면의 실시간 메시지를 비우는 코드가 함께 실행돼 메시지가 사라졌습니다.

해결

다시 연결될 때 보던 채팅방을 다시 구독하도록 앱과 웹을 고치고, 연결이 끊기는 것을 받아 상태에 반영했습니다. 실시간 메시지는 방이 바뀔 때만 비우게 했습니다.

확인한 방법

고친 파일만 되돌려 테스트가 먼저 실패하는 것을 확인한 뒤 고쳤고, 같은 순서로 앱과 웹을 오가며 다시 시험했습니다.

결과

다시 연결된 뒤에도 앱과 웹 모두 메시지를 받습니다.

고치기 전

  1. 연결이 끊김
  2. 다시 연결됨
  3. 예전 구독이 남아 있어 다시 구독하지 않음
  4. 보내기는 되고 받기만 멈춤

고친 뒤

  1. 연결이 끊김, 끊김을 상태에 반영
  2. 다시 연결됨
  3. 보던 채팅방을 다시 구독
  4. 보내기와 받기 모두 동작

더한 테스트 일부 (앱)

  • 다시 붙으면 걸어 둔 구독을 다시 건다
  • 다시 붙어도 푼 구독은 안 살아난다

기록

  • PR #885 웹: 방 구독 다시 걸기 ↗

06 실시간과 결제

테스트 결제에서 금액 조작과 두 번 승인을 막기

예약과 결제 | Next.js, Spring Boot, 토스페이먼츠 테스트 모드

  • 금액 대조
  • 멱등키
  • 예약자 확인

AI 도구와 함께 서버와 웹을 구현

문제

"예약중"은 상품에 붙는 표시일 뿐이었습니다. 서버는 누구와 예약했는지 몰랐고, 예약된 상품에도 누구나 새 채팅을 걸 수 있었으며, 결제 기능은 없었습니다.

원인

결제를 붙이면 브라우저가 보낸 금액은 화면을 조작해 바꿀 수 있고, 결과 화면을 새로고침하면 같은 승인 요청이 다시 갈 수 있습니다.

해결

판매자가 그 상품으로 채팅한 상대 중 한 명을 골라 예약하면, 예약자만 채팅방에서 결제하게 했습니다(토스페이먼츠 테스트 모드). 결제 금액은 브라우저가 보낸 값을 믿지 않고 서버가 저장한 금액, 지금 상품 가격과 대조합니다. 주문마다 같은 멱등키를 붙이고 주문을 잠가 두 번 승인되지 않게 했습니다.

확인한 방법

서버 테스트 10개 이상으로 금액이 다를 때, 상품 가격이 바뀌었을 때, 예약이 풀렸을 때, 남의 주문일 때 승인을 거절하는지, 이미 끝난 주문은 결제사를 다시 부르지 않고 같은 결과를 돌려주는지 확인했습니다. 웹은 결과 화면이 확정 요청을 한 번만 보내는지 테스트했습니다.

결과

금액이 다르거나 예약자가 아니면 승인하지 않고, 결과 화면을 새로고침해도 다시 승인하지 않습니다.

취소, 환불, 웹훅은 하지 않았습니다.

  1. 판매자가 채팅한 상대 중 예약자 선택
  2. 예약자만 채팅방에서 결제
  3. 판매 완료, 채팅방 닫힘

믿지 않는 값

브라우저가 보낸 결제 금액
