Trovely

인스타그램과 유튜브에서 다시 보고 싶은 게시물을 저장하고 검색하는 서비스입니다.

Live ↗ GitHub ↗

프로젝트 개요

개요

인스타그램과 유튜브에서 다시 보고 싶은 게시물을 카테고리, 태그, 메모, 후기와 함께 저장하고 검색하는 서비스입니다. 인스타그램의 저장 기능은 컬렉션 이름으로만 나뉘어 저장한 글 안에서 검색할 수 없는 게 답답해서, 직접 기획하고 혼자 만들어 배포했습니다.

역할
  • 기획: 인스타그램보다 유튜브를 쓰는 사람이 더 많다고 보고 유튜브 영상까지 저장하도록 확장
  • 프론트엔드: Next.js App Router 모바일 웹, 메모와 후기, 태그, 카테고리를 함께 찾는 여러 키워드 검색, 카테고리 필터와 무한 스크롤, 홈 화면 추가(PWA)
  • 서버와 배포: Supabase로 로그인, 데이터 저장, 썸네일 보관을 구성하고 Vercel로 배포
  • 진행 방식: Claude Code로 개발하고, 스프린트마다 테스트 시나리오 문서를 써서 직접 확인
기술

Next.js 16, TypeScript, Tailwind CSS, Vercel, Claude Code

백엔드 (AI와 함께 구현): Next.js Server Actions, Supabase (PostgreSQL, Auth, Storage), Prisma

  2. 02썸네일썸네일 문제를 다시 정해 깨짐 막기갱신 대신 깨짐 방어로
  3. 03조회 성능조회 비용을 줄이기 전에 측정하기측정해 보니 병목이 아니라 캐싱 0줄

01 개발 환경

개발 DB와 운영 DB 나누기

문제

로컬에서 개발할 때도 운영 DB에 연결돼 있어서, 개발 중 실수가 실제 데이터에 그대로 닿을 수 있었습니다.

원인

개발용 DB가 따로 없었습니다. 나누는 작업 중에는 Next.js는 .env.local을 먼저 읽지만 Prisma는 .env만 읽는다는 차이도 발견했습니다. 로컬 주소를 .env.local에만 두면 화면은 로컬 DB를 쓰는데 마이그레이션은 운영 DB에서 실행될 수 있었습니다.

해결

AI 도구와 함께 Docker로 로컬에 Supabase(DB, 로그인, 저장소)를 띄워 개발 DB를 나누고, 운영 값은 주석으로 남겼습니다. 로컬 주소는 .env에 두고, 운영 비밀번호는 로컬에 두지 않고 배포 환경(Vercel)에만 두는 원칙을 세웠습니다.

결과

개발 DB와 운영 DB가 나뉘었고, 운영 비밀번호는 로컬 디스크에 남지 않습니다.

.env.local에만 둘 때

Next.js 화면은 로컬 DB

Prisma 마이그레이션은 운영 DB

.env에 둘 때

Next.js 화면도, Prisma 마이그레이션도 로컬 DB

운영 값은 배포 환경(Vercel)에만

02 썸네일

썸네일 문제를 다시 정해 깨짐 막기

문제

처음에는 게시자가 썸네일을 바꾸면 이를 어떻게 알아채고 갱신할지를 고민했습니다.

원인

Trovely는 내가 모은 것을 다시 보는 도구라서, 게시자의 변경을 따라가는 것보다 저장한 썸네일이 만료나 삭제로 안 보이는 것이 사용자가 실제로 겪는 불편이라고 판단했습니다.

해결

문제를 "깨짐 방어"로 다시 정했습니다. AI 도구와 함께, 저장할 때는 이미지를 저장소에 영구 보관하고 일시 실패는 최대 3번 다시 시도하며, 화면에서 깨지면 서버에서 다시 찾아 그 자리에서 바꿔 끼우게 했습니다.

확인한 방법

서버에서 그린 이미지가 화면 연결 전에 실패하면 깨짐을 놓쳐 "가끔만 동작"하던 문제를 찾았습니다. 화면이 뜬 뒤 이미 깨진 이미지인지 한 번 더 확인하게 고쳤습니다.

결과

저장한 썸네일이 깨져도 그 자리에서 다시 찾아 바꿔 끼우고, 끝내 못 찾으면 빈 자리 대신 대체 아이콘을 보여 줍니다.

처음 질문

게시자가 썸네일을 바꾸면 알아채고 갱신

외부에서 알려 주는 장치가 없으면 사실상 어렵고, 다시 보기 도구에선 가치가 낮음

다시 정한 문제

저장한 썸네일이 깨지지 않게

저장할 때 영구 보관과 재시도, 깨졌을 때 다시 찾아 바꿔 끼움

03 조회 성능

조회 비용을 줄이기 전에 측정하기

문제

이미지를 매번 DB에서 조회하는 비용을 어떻게 줄일지 고민하며, 캐싱부터 만들려고 했습니다.

원인

DB에는 이미지 주소만 있고 이미지는 저장소에 있어서, "DB에서 이미지를 조회한다"는 표현부터 다시 따져 볼 필요가 있었습니다. 지금 규모에서 정말 병목인지도 확인하지 않은 상태였습니다.

해결

AI 도구의 제안으로 캐싱을 만들기 전에 병목인지부터 측정했습니다. AI 도구로 테스트 데이터를 넣고 EXPLAIN ANALYZE로 기본 목록과 검색 쿼리 시간을 쟀습니다.

확인한 방법

1,000건과 50,000건에서 각각 쟀고, 50,000건에서도 기본 목록 18ms, 검색 14ms로 사람이 느끼지 못하는 수준이었습니다.

결과

캐싱은 복잡도만 늘린다고 보고 만들지 않았습니다(캐싱 코드 0줄). 데이터가 커지면 목록은 복합 인덱스, 검색은 전문 검색 순으로 적용할 계획만 정리했습니다.

EXPLAIN ANALYZE 측정 결과
쿼리1,000건50,000건
기본 목록0.4ms18ms
검색0.4ms14ms
