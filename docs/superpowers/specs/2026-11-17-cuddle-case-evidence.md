표시 규칙

## 01. 첫 HTML에서 빠진 이미지를 찾아 홈 화면 로딩 줄이기 (AI 도구와 함께)

- 문제 [원본]: 홈 화면 LCP(가장 큰 요소가 보이기까지의 시간)가 1.3초였고, 그중 0.9초는 브라우저가 이미지 주소를 찾기까지 기다린 시간이었다.
- 원인 [원본]: 로딩 중 화면이 화면 코드가 실행된 뒤에야 만들어져서, 첫 HTML에 이미지가 하나도 없었다.
- 원인 보강 [저장소]: 홈은 `useSearchParams()` 때문에 `<Suspense>`로 감싸져 있었고, 서버는 이미지 주소가 없는 스켈레톤(`HomeSkeleton`)만 먼저 보냈다. 이미지를 찾기까지 걸린 시간(Load Delay)은 917ms로 측정됐다. 출처: `docs/lighthouse-optimization-log.md` 5차 분석
- 해결 [원본]: 로딩 중 화면을 서버 컴포넌트로 바꿔 첫 HTML에 이미지가 담기게 했다. 60초마다 페이지를 다시 만드는 방식은 그대로 두었다.
- 시도 순서 [원본]: 시도 1 서버에서 상품 데이터를 미리 받아 넘김(1.3초, 변화 없음), 시도 2 이미지 미리 받기(1.2초, 점수 94에서 91), 시도 3 로딩 처리를 걷어 냄(점수 83, 바로 되돌림), 해결(1.0초, 94점)
- 확인한 방법 [원본]: 시도할 때마다 Lighthouse와 DebugBear로 다시 측정했다. AI 도구로 수정안을 만들고, 시도마다 직접 다시 측정해 채택할지 되돌릴지 정했다.
- 확인한 방법 보강 [저장소]: 바꾸기 전과 후의 첫 HTML을 열어 이미지 태그 수를 셌다. 바꾸기 전 0개, 바꾼 뒤 22개(로고 2개, 상품 이미지 20개). 출처: 같은 문서 6차 분석 "검증"
- 결과 [원본]: LCP 1.3초에서 1.0초(약 23% 단축), 성능 점수 94점 유지. FCP(첫 콘텐츠가 보이는 시간) 0.4초에서 0.9초, CLS(화면 흔들림) 0에서 0.008
- 불리한 숫자의 이유 [저장소]: FCP가 늘어난 것은 첫 HTML이 커져 첫 화면을 그리기까지 시간이 늘었기 때문이고, CLS는 서버 화면이 실제 화면으로 바뀔 때 생긴 작은 흔들림이다. 출처: 같은 문서 6차 분석 결과
- 근거 링크 [저장소]: PR #262(서버에서 초기 데이터 받기), #263(이미지 미리 받기 전략), #265(서버 컴포넌트로 교체), 측정 기록 문서

## 02. 관리 화면 8개를 설정 파일 하나로 만드는 공통 테이블 (AI 도구와 함께)

- 문제 [원본]: 회원, 상품, 커뮤니티, 신고 등 관리 화면마다 표와 필터, 정렬, 페이지 처리가 따로 필요했다.
- 원인 [확인 필요]: 원본에는 "화면마다 따로 필요했다"까지만 있다. 원인 칸은 "화면마다 같은 표 기능을 따로 만들면 8번 반복하게 된다" 정도로 문제를 풀어 쓰는 수준으로 두려고 한다. 괜찮은지 확인해 줘.
- 해결 [원본]: 설정 파일로 화면을 정의하는 공통 테이블과 커스텀 훅(`useAdminTable`)을 만들어 8개 화면을 하나의 구조로 묶었다. 새 화면은 설정 파일 하나와 짧은 페이지 코드로 만든다. 열 종류는 6가지(글자, 숫자, 금액, 배지, 날짜, 이미지)
- 확인한 방법 [확인 필요]: 저장소에 공통 테이블 자체의 테스트는 없다. 관련 기록은 관리자 데모 모드(PR #770, 2026-06-27)로 데모 데이터를 넣어 화면을 띄울 수 있게 한 것이다. "8개 화면을 데모 데이터로 띄워 표, 검색, 정렬, 페이지 이동이 같은 방식으로 동작하는지 직접 확인했다"고 써도 되는지, 실제로 어떻게 확인했는지 알려 줘.
- 결과 [원본]: 관리 화면 8개, 공통 테이블과 훅 646줄, 화면별 설정 파일 52~124줄, 새 화면의 페이지 코드 7줄
- 숫자 차이 [확인 필요]: 지금 저장소에서는 공통 테이블과 훅이 629줄, 상품 관리 페이지 코드가 27줄이다(이후 상세 보기 창이 더해짐). 결정한 대로 PDF 값(646줄, 7줄)을 쓰되, "PDF 작성 시점 기준"이라고 따로 적지는 않을 계획이다.
- 근거 자료: 상품 관리 화면 그림(데모 데이터), `productTableConfig.ts` 일부, `ProductsManagement.tsx`의 `<AdminTable>` 부분, PR #384(기초), #386(테이블 코어), #389, #392, #393(화면들)

## 03. AI 코드 리뷰가 실제 버그만 짚도록 지시문 좁히기 (표시 없음)

- 문제 [원본]: 처음 지시문은 코드 품질, 버그, 성능, 보안, 모범 사례를 모두 보게 해서, 일어나기 어려운 예외 상황과 과한 방어 코드 지적이 많아 읽히지 않았다.
- 원인 [원본에서 정리]: 지시문이 볼 것을 너무 넓게 정해서, 실제로 고칠 지적과 그렇지 않은 지적이 섞였다.
- 해결 [원본]: 실제 버그, 명백한 성능 문제, Next.js와 React에서 피해야 할 작성 방식만 보게 지시문을 좁혔다.
- 확인한 방법 [원본]: 리뷰가 Escape 키 처리가 빠졌다고 짚었을 때 직접 동작을 확인했다.
- 확인한 방법 보강 [저장소]: 그 컴포넌트는 방향키는 단추가, Escape는 문서 전체의 키 입력 감지가 따로 잡고 있어서 리뷰가 잘못 본 것이었다. 코드는 그대로 두고, 왜 나뉘어 있는지 밝히는 주석 3줄을 더했다. 출처: 커밋 5c65db15(PR #1070의 Kimi 리뷰), 지시문 변경 커밋 a44c4efe(PR #269)
- 결과 [원본]: 리뷰가 헷갈린 곳은 사람도 헷갈린다고 보고 코드 대신 의도를 밝히는 주석을 더했다.
- 알릴 점 [확인 필요]: 지시문을 고친 커밋 a44c4efe에도 Claude 공동 작성 표시가 있다. 03은 표시하지 않기로 했는데, 그대로 둘지 확인해 줘.

## 04. 모든 PR에서 타입 검사, 린트, 테스트, 빌드가 돌게 하기 (AI 도구와 함께)

- 문제 [원본]: 워크플로가 셋 있었지만 그 안에 타입 검사, 린트, 테스트, 빌드가 없어서, 테스트를 깨뜨린 PR도 병합될 수 있었다.
- 원인 [저장소]: 검사는 사람이 손으로 돌리는 것뿐이었고, 잊으면 그대로 통과했다. 커밋 메시지 검사 규칙도 설정만 있고 실행하는 장치(husky)가 없어서 한 번도 돌지 않았다. 출처: 커밋 bbfbe4fa(PR #1018)
- 해결 [원본]: PR마다 공통 패키지, 앱, 웹 세 작업이 나란히 타입 검사, 린트, 테스트, 빌드를 돌게 했다.
- 해결 보강 [저장소]: 한 작업에서 순서대로 돌리면 앞이 깨질 때 뒤를 못 보고 시간도 셋의 합이 되어서 셋으로 나눴다. 문서만 바뀐 PR은 검사를 건너뛰게 했다(PR 아홉 중 넷이 문서만 바뀐 것이었고, 그중 하나는 39분을 기다렸다). 출처: `.github/workflows/gate.yml` 주석, 커밋 70c7ec44
- 확인한 방법 [원본]: 고친 줄을 일부러 빼 보고 테스트가 실패하는지 확인해, 그 테스트가 정말 그 코드를 지키는지 검증했다.
- 결과 [원본]: 테스트 파일 136개(웹 46, 앱 77, 공통 패키지 13). 재전송이 실패해도 아무 안내가 없던 문제를 테스트가 먼저 잡았다.
- 숫자 차이 [확인 필요]: 지금 저장소는 154개(웹 64, 앱 77, 공통 13)다. 결정한 대로 PDF 값 136개를 쓴다.
- 근거 못 찾음 [확인 필요]: "재전송 실패 안내를 테스트가 먼저 잡은 일"의 커밋을 찾지 못했다. 원본 문장 그대로 둬도 되는지 확인해 줘.
- 근거 자료: 실제 `gate.yml` 일부(on, jobs 이름), 테스트 수, PR #1018 링크

## 05. 다시 연결된 뒤 앱 화면에 메시지가 안 보이던 문제 고치기 (AI 도구와 함께)

- 문제 [원본]: 휴대폰 앱과 웹을 오가며 직접 시험하다가, 연결이 끊겼다 다시 이어진 뒤 앱에서 보낸 메시지가 웹에는 가지만 앱 화면에는 보이지 않는 문제를 발견했다.
- 원인 [저장소]: 다시 연결되면 예전 구독은 끊긴 연결에 남은 빈 껍데기인데, 코드는 구독이 이미 있다고 보고 건너뛰었다. 그래서 새 연결에는 구독이 하나도 없었다. 보내기는 새 연결로 잘 나가서 오류도 안내도 없이 받기만 멈췄다. 연결이 끊긴 것을 기록하는 곳도 없어서 "연결 중" 안내가 뜨지 않았다. 출처: 앱 커밋 15ca03fb(PR #883), 웹 커밋 21999fd0(PR #885)
- 해결 [원본+저장소]: 다시 연결될 때 보던 채팅방을 다시 구독하도록 앱과 웹을 고치고, 연결이 끊기는 것을 받아 상태에 반영했다.
- 두 번째 문제 [확인 필요]: 원본에는 "메시지 중복을 막던 코드가 재연결 때 받은 메시지를 지우던 문제"라고 적혀 있다. 저장소 기록(PR #885)에는 "다시 연결될 때마다 화면의 실시간 메시지를 비우는 코드(`clearRoomMessages`)가 함께 실행돼 메시지가 사라졌고, 이제 방이 바뀔 때만 비운다"고 적혀 있다. 두 설명이 같은 문제인지 확인해 줘. 같다면 저장소 기록 쪽 표현으로 쓰려고 한다.
- 확인한 방법 [원본+저장소]: 같은 순서로 앱과 웹을 오가며 다시 시험했다. 고친 파일만 되돌려 테스트가 먼저 실패하는 것을 확인한 뒤 고쳤다(앱 테스트 4개, 웹 소켓 저장소 테스트 새로 작성). 출처: 위 두 커밋 메시지, `mobile/lib/chat/socket.test.ts`("다시 붙으면 걸어 둔 구독을 다시 건다" 등), `src/store/chatSocketStore.test.ts`
- 결과 [원본+저장소]: 다시 연결된 뒤에도 앱과 웹 모두 메시지를 받는다.
- 근거 자료: 고치기 전과 후 흐름 그림, 앱 테스트 이름 목록 또는 코드 일부, PR #883, #885

## 06. 테스트 결제에서 금액 조작과 두 번 승인을 막기 (AI 도구와 함께)

- 문제 [원본]: "예약중"은 상품에 붙는 표시일 뿐이었다. 서버는 누구와 예약했는지 몰랐고, 예약된 상품에도 누구나 새 채팅을 걸 수 있었으며, 결제 기능은 없었다.
- 원인 [저장소]: 결제를 붙이면 브라우저가 보낸 금액은 화면을 조작해 바꿀 수 있고, 결과 화면을 새로고침하면 같은 승인 요청이 다시 갈 수 있다. 출처: 백엔드 `PaymentService.java` 주석("웹이 보낸 금액은 바꿔치기될 수 있어 저장한 값과 대조한다"), `TossPaymentGateway.java` 주석
- 해결 [원본]: 판매자가 그 상품으로 채팅한 상대 중 한 명을 골라 예약하면, 예약자만 채팅방에서 결제하게 했다(토스페이먼츠 테스트 모드). 결제 금액은 서버가 저장한 금액, 지금 상품 가격과 대조한다. 주문마다 같은 멱등키(`Idempotency-Key: confirm-주문번호`)를 붙이고 주문을 잠갔다.
- 확인한 방법 [저장소]: 서버 테스트로 받은 금액이 다를 때, 상품 가격이 바뀌었을 때, 예약이 풀렸을 때, 남의 주문일 때 승인을 거절하는지, 이미 완료된 주문은 결제사를 다시 부르지 않고 같은 결과를 돌려주는지 확인했다(`PaymentServiceTest` 12개). 웹은 결과 화면이 확정 요청을 한 번만 보내는지 테스트했다(`PaymentSuccess.test.tsx`). 출처: 백엔드 커밋 a995a26, 웹 PR #1127
- 결과 [원본]: 취소, 환불, 웹훅은 하지 않았다.
- 근거 자료: 예약에서 판매 완료까지 흐름, 믿지 않는 값과 확정 조건 비교, 멱등키 한 줄, 서버 테스트 이름 일부, PR #1127
- 링크 주의 [확인 필요]: 백엔드 코드는 팀원 소유 공개 저장소(`jinioh88/cmarket_api`)에 있고, 이 저장소의 커밋 기록에는 아직 재발급하지 않은 비밀 값이 남아 있다. 비밀 값을 재발급하기 전까지는 상세 페이지에 백엔드 저장소 링크를 넣지 않고, 웹 PR #1127 링크만 넣는 것을 권한다.
