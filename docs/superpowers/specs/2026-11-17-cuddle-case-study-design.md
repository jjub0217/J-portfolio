# Cuddle Market 상세 페이지 설계

작성일: 2026-11-17 (화)
상태: 사용자 검토 대기 (2026-11-17 질문 2개 반영)

## 1. 왜 만드는가

웹 포트폴리오의 프로젝트 카드 7개는 모두 운영 중인 서비스나 GitHub로 바로 연결된다. 그래서 채용 담당자가 "어떤 문제를 어떻게 판단해서 풀었는지"를 사이트 안에서 읽을 곳이 없다. 이런 설명은 포트폴리오 PDF에만 있다.

Cuddle Market 상세 페이지는 PDF의 Cuddle 내용을 사례별로 다시 정리해서, 담당자가 판단 과정을 편하게 읽게 하는 페이지다. 참고한 틀은 네이버 크림 인턴 합격자의 포트폴리오다. 사례마다 같은 순서의 칸을 쓰고, 왼쪽에는 글, 오른쪽에는 근거 자료를 두고, 결과만 강조색으로 보여 준다.

## 2. 목표

- 담당자가 맨 위에서 프로젝트 개요와 링크(Live, Admin Demo, GitHub)를 바로 확인한다.
- 빠른 목차에서 원하는 사례로 바로 이동한다.
- 사례 6개를 모두 "문제, 원인, 해결, 확인한 방법, 결과"라는 같은 순서로 읽는다.
- 메인 페이지의 Cuddle 카드를 누르면 이 상세 페이지로 온다.

## 3. 하지 않을 것

- 나머지 6개 카드(글모험, Wavve, jjub-headless-ui, Trovely, Chanel, claude-code-skills)의 상세 페이지와 링크 변경. 이 카드들은 지금처럼 외부 서비스나 GitHub로 바로 간다.
- Trovely("Demo")와 jjub-headless-ui("npm") 카드의 배지 구조 정리. 같은 문제가 있지만 별도의 작은 작업으로 한다.
- 메인 카드에 Live, GitHub, "Case Study →" 같은 버튼이나 문구를 더하는 것.
- 크림 포트폴리오의 회사 맞춤 요소("입사 후 해보고 싶은 일", 회사 로고, 마지막 쪽의 회사 연결 그림). 모든 회사가 보는 페이지라 넣지 않는다.

## 4. 실패로 보는 경우 (기술적으로 동작해도)

- PDF나 저장소에 없는 사실, 숫자, 성과가 들어간다. 특히 AI 도구와 함께 만든 부분을 혼자 만든 것처럼 쓴다.
- 불리한 숫자를 뺀다. 홈 화면 로딩 개선에서 FCP가 0.4초에서 0.9초로, CLS가 0에서 0.008로 늘어난 것도 반드시 적는다.
- 스크롤에 따라 날아오는 효과, 저절로 움직이는 화면, 가로 스크롤이 생긴다.
- 휴대폰에서 글이나 표가 화면 밖으로 넘친다.
- 메인 페이지의 Cuddle 카드 모양이나 마우스 반응이 지금과 달라 보인다.

## 5. 사용자가 정한 것

### 5-1. 범위와 주소
- 상세 페이지는 Cuddle Market 하나만 만든다. 주소는 `projects/cuddle.html`이다(배포 주소 `https://jjub0217.github.io/J-portfolio/projects/cuddle.html`).
- 메인 페이지에서는 Cuddle 카드만 상세 페이지로 연결하고, 나머지 6개 카드는 그대로 둔다.

### 5-2. 메인 페이지 Cuddle 카드
- 카드 전체를 누르면 `./projects/cuddle.html`로 간다. 같은 탭에서 연다(사이트 안의 페이지이므로 `target="_blank"`를 쓰지 않는다).
- 제목 "→ Cuddle Market (Team → Solo)"와 마우스를 올렸을 때의 반응(제목이 밀리고 흰 배경이 차오르는 효과)은 지금과 똑같이 둔다. "Case Study →" 같은 문구는 더하지 않는다.
- 썸네일 오른쪽 아래의 "Admin Demo ↗" 배지는 보이는 위치와 모양을 그대로 둔다. 다만 코드 구조는 바꾼다.
  - 지금은 카드 링크(`<a class="work_link">`) 안에 `<span role="link" onclick=…>`으로 들어 있어서, 링크 안에 링크가 있는 구조이고 키보드 Enter로 열리지 않을 가능성이 크다.
  - 바꾼 뒤에는 배지를 카드 링크 밖의 진짜 링크(`<a href="…admin" target="_blank" rel="noopener">`)로 만들고, 카드와 배지를 감싸는 상자 안에서 썸네일 위에 겹쳐 놓는다.
  - Tab으로 카드 링크와 배지 링크에 각각 도착하고, Enter로 각각 열려야 한다. 화면 낭독기에는 배지가 "관리자 데모 새 탭에서 열기"처럼 읽혀야 한다.
  - Admin Demo 주소는 지금 코드에 있는 `https://cuddle-market-git-feature-admin-demo-mode-jjub0217s-projects.vercel.app/admin`을 그대로 쓴다.

### 6-1. "원인"과 "확인한 방법" 칸 채우기 (사용자 결정, 2026-11-17)
- 원본 PDF는 대부분 "고치기 전"과 "고친 뒤" 두 칸뿐이라, 다섯 칸을 모두 채우려면 원본 밖의 근거가 필요하다.
- 01번 확인한 방법은 원본 그대로 쓴다(Lighthouse와 DebugBear로 시도마다 다시 측정).
- 나머지 칸은 Cuddle 저장소(`~/Desktop/cuddle-market`)의 코드, 테스트, PR, 커밋, 문서를 근거로 초안을 쓴다. 사용자가 예로 든 방법(브라우저 네트워크 탭에서 주고받은 데이터 확인, 로컬 테스트와 오류 기록 확인 등)은 저장소에 근거가 있거나 사용자가 실제로 했다고 확인한 경우에만 쓴다.
- 원본에 없던 문장은 페이지에 넣기 전에 "문장, 근거(파일 경로나 PR 번호), 근거 없음 여부" 목록으로 사용자에게 보여 주고, 사용자가 확인한 것만 넣는다.
- 근거가 없는 칸은 사용자에게 실제로 어떻게 확인했는지 묻는다. 지어내지 않는다.

### 6-2. "AI 도구와 함께" 표시 (사용자 결정, 2026-11-17)
- 방향: AI를 도구로 쓰고, 구조 설계와 최종 확인은 본인이 맡았다는 뜻이 드러나게 쓴다. "AI가 다 해 줬다"로 읽히지 않게 한다.
- 표시할 사례: 01, 02, 04, 05, 06.
  - 01: 원본에 "AI 도구로 수정안을 만들고, 시도마다 직접 다시 측정해 채택할지 되돌릴지 정했습니다"가 있다.
  - 02: 저장소의 관리 화면 작업(2026-03-05, #372~#375)에 Claude 공동 작성 표시가 붙은 커밋이 여러 개 있다(예: 1f317a25, 62c6fdcc, d08dec73).
  - 04: CI 검사를 붙인 커밋 bbfbe4fa(#1017, 2026-08-22)에 Claude 공동 작성 표시가 있다.
  - 05, 06: 원본에 "AI 도구와 함께"가 있다.
- 03(AI 코드 리뷰 지시문)은 AI 리뷰 도구를 다루는 사례라 따로 표시하지 않는다. 지시문을 고치고 잘못된 지적을 직접 확인한 것은 본인이 한 일로 쓴다.

### 6-3. 만드는 사람이 정한 것 (사용자가 확인할 것)
- 코드는 `~/Desktop/cuddle-market`(최신 커밋 2026-11-13)의 실제 파일에서 일부를 가져오고 파일 경로를 적는다. 04번 검사 설정도 실제 파일의 일부를 쓴다.
- 숫자는 PDF 값을 쓴다. 지금 저장소 값이 다르면 바꾸지 않고 사용자에게 먼저 알린다.
- 05번 흐름 그림은 원본 문단을 바탕으로 그리고, 메시지 중복을 막던 코드가 다시 연결될 때 받은 메시지를 지우던 두 번째 문제도 넣는다.

- 사례 제목은 위 표의 문장을 기본으로 하되, 다듬을 때도 원본에 없는 주장을 넣지 않는다.
- 그림은 원본 폴더의 `img/`에서 복사해 `assets/images/cuddle/`에 둔다. 그림이 없는 사례(01, 03, 04, 05, 06)는 표, 흐름 그림, 코드로 근거를 채운다. 화면 캡처가 더 필요하면 사용자에게 요청한다.
- `img/alert-flood-night.png`(30분마다 쌓이던 알림)는 이번 6개 사례에 해당하지 않으므로 쓰지 않는다.
- PR 링크는 `gh`로 `jjub0217/cuddle-market`에서 실제로 찾은 PR만 넣는다. 못 찾은 사례는 PR 링크를 넣지 않고, 있는 경우 관련 문서나 커밋 링크로 대신한다.

## 9. 제약

- 사이트는 프레임워크 없는 정적 HTML이고, GitHub Pages가 `main` 브랜치에서 배포한다. 빌드 과정이 없다.
- 상세 페이지는 `projects/` 폴더 안에 있으므로, CSS, 그림, PDF 경로는 `../`로 시작해야 한다.
- 메인 페이지의 `main.js`는 메인 페이지의 요소(GSAP 효과, 첫 화면, 공 등)를 전제로 동작하므로, 상세 페이지에서 그대로 불러오면 오류가 날 수 있다.
- 사이트는 `html, body { height: 100%; }`이고 실제로 스크롤되는 것은 `body`다. 목차 이동은 이 구조에서 동작해야 한다.
- 메인 카드 목록(`.works_box`)은 카드 링크를 바로 아래 자식으로 두는 배치(2개, 3개, 2개 줄)다. Cuddle 카드를 감싸는 상자를 더해도 배치가 달라 보이면 안 된다.
- 로컬에서 지워진 파일 세 개(`img_work_item2.mp4`, `img_work_item8.mp4`, `img_nextjs_logo.png`)는 커밋에 넣지 않는다.
- 작업 브랜치 `feat/cuddle-case-study`에서 하고, 커밋, 푸시, PR은 사용자가 요청할 때만 한다. 머지는 사용자가 한다.

## 10. 만드는 사람에게 맡기는 것

- CSS를 기존 `style.css`에 더할지, 상세 페이지 전용 파일을 따로 둘지
- 상세 페이지에서 쓸 스크립트의 구성(목차 이동, 그림 크게 보기, 코드 복사)
- 사이트 헤더와 푸터를 상세 페이지에서 어떻게 다시 쓸지(메뉴는 `../index.html#about` 같은 메인 구역 주소로)
- 키워드 칩 문구, 한 줄 결과 문구의 세부 표현(원본 사실 범위 안에서)
- 그림 크게 보기를 어떤 방식으로 만들지(키보드로 닫을 수 있어야 함)

## 11. 확인 방법

- 화면 폭 1400px, 990px, 375px, 320px에서 가로 스크롤이 없고 글과 표가 넘치지 않는다.
- 목차를 누르면 해당 사례로 이동하고, 움직임 줄이기 설정에서는 바로 이동한다.
- 메인 페이지에서 Cuddle 카드를 누르면 상세 페이지로 가고, 배지를 누르면 Admin Demo가 새 탭에서 열린다. 키보드 Tab과 Enter로도 각각 동작한다.
- 메인 카드의 모양과 마우스 반응이 바뀌기 전과 같다(바꾸기 전과 후 캡처 비교).
- 상세 페이지의 모든 숫자와 문장을 원본 HTML과 대조한다.
- 모든 링크가 열린다.
